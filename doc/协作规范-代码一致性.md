# 协作规范：两位负责人的代码一致性方案

> 项目：MIPI-HDMI 实时视频图像处理系统（安路 PH1P35 + SC520CS）
> 涉及：**张金艺**（扩展2 目标检测与识别）、**张铭晨**（进阶2 跟踪 + 进阶4 运动检测）
> 依据：《开发方案B-目标检测跟踪与运动检测》§1 共同基础、§4 接口约定
> 编写日期：2026-10-10

---

## 0. 一句话结论

**不要"共用大模型"或"共用账号"。** 保证底层一致的正道是四件事：

1. **两人进同一仓库、各用各的分支**（Collaborator 权限，不是共享账号）；
2. **公共基础代码只保留唯一一份**（`common_base/`，谁都不许复制）；
3. **接口先冻结成文件**（信号、位宽、时序、取值域，全部写死）；
4. **合板前用同一套位级对拍脚本互验**（复用 D1 已建好的验证链路）。

---

## 1. 为什么"共用一个 AI 账号"解决不了问题

这是最容易被想到、但方向完全错误的办法。

### 1.1 AI 生成是不确定的

同一个 prompt 跑两次，产出的 RTL 都不一样。哪怕你们俩用同一个模型、同一句话，各写一遍"RGB→YCbCr"，结果仍会有：

- **系数差**：BT.601 有 77/150/29 与 76.5/150/29.5 等多种取法，四舍五入位置也不同；
- **流水级数差**：有人写 2 拍、有人写 3 拍、有人 4 拍；
- **限幅/取整顺序差**：先限幅再比较 vs 先比较再限幅，D1 里正是这个导致纯红漏检；
- **位宽差**：中间和用 18bit 还是 20bit，补码溢出边界不同。

> **实证**：D1 阶段真实抓到两个 BUG ——「时序延时多一拍导致首像素丢失」和「未限幅导致纯红/纯蓝漏检」。这两个都是**功能级仿真看起来对、位级对拍才现形**的差异。两个用 AI 各写一遍的人，撞上这两种差异的概率极高，而且到合板那天才会集中爆发。

### 1.2 合板炸掉的真正原因不是"谁写的"

合板出问题，99% 是下面三类，**与代码作者是谁无关**：

| 类型 | 典型表现 | 本例中的风险点 |
|:---|:---|:---|
| **接口不对齐** | 信号名/位宽/有效电平不一致，综合能过、上板全黑 | 方案B §4 的目标列表总线格式至今未定义 |
| **坐标系不一致** | 框画偏、坐标错乱 | §1.3 要求公共坐标由队长在 top 生成，但你的模块自建了一套计数器 |
| **时序/取整不一致** | 掩膜边界差 1 像素、颜色阈值边缘抖动 | 两人的连通域如果各写一份，label 编号规则必然不同 |

### 1.3 共用账号的额外风险

- **合规风险**：共享账号通常违反服务条款，属于比赛纪律问题；
- **留痕失效**：比赛看重"分工与过程"，共用账号会让提交记录无法区分两人的工作量，**直接损失加分材料**；
- **无助于一致性**：见 1.1，AI 的不确定性不因"同一个账号"而消失。

> ✅ **正确类比**：两个工程师用同一台电脑、同一个编译器，照样写出不兼容的代码。一致性来自**协议**，不来自工具。

## 2. 方案总览（四层防线）

```
┌─────────────────────────────────────────────────────────────┐
│  第 4 层  合板前双人对拍  同一份激励 → 两套 RTL → 逐位比对   │
├─────────────────────────────────────────────────────────────┤
│  第 3 层  接口冻结        总线格式写进 .vh 宏 + 冻结表文档    │
├─────────────────────────────────────────────────────────────┤
│  第 2 层  公共基础模块    common_base/ 唯一实现，禁止复制    │
├─────────────────────────────────────────────────────────────┤
│  第 1 层  仓库与分支      同仓 Collaborator，各自分支 + PR   │
└─────────────────────────────────────────────────────────────┘
```

越往下越基础，**第 1、2 层做扎实，第 3、4 层就轻松**。

## 4. 第 2 层：公共基础模块 `common_base/`

### 4.1 为什么必须集中

方案B §1 明确："两人共用一套『取数 + 连通域 + OSD』基础设施"。**"共用一套"的唯一可靠实现方式，是物理上只有一份文件。**

```
user_source/hdl_source/
├── common_base/                ← ★ 新增：两人共同维护，唯一实现
│   ├── README.md                   使用与修改规则
│   ├── common_defs.vh              全局常量、位宽、宏（含 target_bus 格式）
│   ├── ycbcr_convert.v             RGB888 → YCbCr（从 D1 抽出）
│   ├── （坐标计数器由 track_box/pix_coord_gen.v 提供，不在此目录）
│   ├── conn_label.v                游程法连通域（D2 一起写，张金艺主导）
│   ├── conn_features.v             帧末特征统计：面积 / Σx / Σy / bbox
│   ├── div_shift_sub.v             移位-减法除法器（消隐期质心除法）
│   └── target_bus.v                目标列表总线打包/解包（接口适配）
├── detect_zjy/                 ← 张金艺私有：分类 + OSD 文字
└── track_zmc/                  ← 张铭晨私有：跟踪 + 运动检测 + 画框
```

### 4.2 `common_base/` 使用规则（写进 README，不可违反）

1. ❌ **禁止复制粘贴** `common_base/` 里任何内容到自己目录 —— 要用就实例化或 `` `include ``；
2. ✅ 私有目录只放**两人不共用**的逻辑（分类规则、跟踪算法、OSD 排版）；
3. ⚠ 改 `common_base/` 必须：提 PR → 另一人 review → 说明**为什么改、影响谁**；
4. 🔒 改接口相关文件（`common_defs.vh` / `target_bus.v`）需**双方同意**并更新冻结表版本号；
5. 📌 每个公共模块必须自带 testbench，且 testbench 也要进版本库。

### 4.3 归属与主导权

| 模块 | 主导 | 说明 |
|:---|:---|:---|
| `ycbcr_convert.v` | 张金艺 | D1 已完成位级验证，直接抽出复用 |
| `pix_coord_gen.v` | 张铭晨 | 统一坐标系，避免 §1.3 的"各写一份"问题（原 `common_base/pix_counter.v` 已删除） |
| `conn_label.v` / `conn_features.v` | 张金艺（张铭晨配合） | 方案B 定位为"甲的核心任务"，但**运动检测也要用**，所以必须公共 |
| `target_bus.v` | 两人共同 | 接口适配层，改动需双签 |
| 帧差存储 / 形态学 | 张铭晨 | 他私有，但形态学如需行缓存，复用 `line_delay_ram.v` |

> 💡 **关键洞察**：方案B §4 里"晨→郭：连通域每像素 label 输出"和"艺→晨：目标列表总线"，说明**连通域模块是张铭晨的强依赖**。如果各写一份，label 编号规则不同，画框会框错位置。**这就是必须公共化的最硬理由。**

## 5. 第 3 层：接口冻结

详见同目录 **`接口冻结表.md`**。核心原则：

1. **所有跨人信号必须有明确的位宽、方向、时钟域、有效电平、取值域**；
2. **接口一旦冻结，改动需双签**，并在冻结表里升版本号 + 记录；
3. **总线上的一切"帧末有效"信号，统一以 `vsync` 上升沿锁存**（方案B §4 规定）；
4. **坐标系统一为**：`x: 0~1279`、`y: 0~719`，`de` 有效时计数，帧起始清零。

## 6. 第 4 层：合板前双人对拍

### 6.1 复用已有验证链路

D1 已建成 **Icarus Verilog + 解析派 Python 位级对拍** 的完整链路：

```
user_source/hdl_source/detect_zjy/
├── tb_detect_color_mask.v      激励
├── verify_color_mask.py        从 RTL 原文正则提取系数 → 逐位比对
└── run_verify.sh               一键：编译 → 仿真 → 对拍
```

**这套链路要升级为"公共验证基础设施"**，建议迁到：

```
user_source/verify/              ← ★ 公共验证目录
├── run_verify.sh                    统一入口（带参数：指定 DUT）
├── golden/                          黄金参考模型（Python）
│   ├── ycbcr_ref.py
│   ├── conn_label_ref.py
│   └── features_ref.py
├── stim/                            公共激励（位图 / 视频流）
│   ├── gen_stim.py                  生成确定性激励
│   └── stim_frame.hex
└── README.md                        使用说明
```

### 6.2 对拍流程（每次集成前必做）

```
① 两人各自模块 → 用同一份 stim/ 激励跑仿真 → 输出 .hex
② 与 golden/ Python 模型比对 → 逐位一致才算通过
③ 接口级联测试：把你的 detect 输出接他的 track 输入，跑一帧
④ 通过 → PR 合并到 main；不通过 → 定位到人、定位到拍
```

### 6.3 为什么必须位级（而不是功能级）

方案B §7 的血泪经验明确写了：本项目历史上几个重大 BUG（色度降噪 Y 被除 256、Verilog 部分选择无符号、`ae_meter` 常量除法位宽）**全是功能级仿真看不出来、位级仿真才抓到的**。

> **功能级"看起来对"不算对。** 仿真里要真的按位宽截断、按补码运算。
